# SkyNet Terminal

**Cyberdyne Systems / Skynet** — кинематографичное загрузочное шоу, которое целиком
играется в терминале. Ни окна, ни видео: белый «хакерский» пролог, сборка логотипа
из шума, радар, покадровое сканирование T-800 в Sixel-графике, оранжевая панель ТТХ
и финальный звонок.

Версия: **2.5.3** · Платформа: **Windows 10/11** · Язык: **PowerShell 7** / **PowerShell 5.1**

## Быстрый старт

```powershell
git clone https://github.com/mrzsrg/SkyNet-Terminal.git
cd SkyNet-Terminal

# chafa обязателен для Sixel-графики
winget install hpjansson.Chafa

# запуск в максимизированном Windows Terminal
.\Core\start_skynet_fullscreen.ps1
```

Из репозитория или из zip-архива шоу запускается одной командой. Всё, что нужно
сделать вручную, — поставить [chafa](https://hpjansson.org/chafa/) и запускать
показ в терминале с поддержкой Sixel.

## Требования для идеальной визуализации

Шоу **намеренно требовательно** к окружению: оно рассчитано на полноэкранный
терминал с настоящей графикой, а не на «цветной текст в консоли». Ниже — что
влияет на картинку напрямую.

### Обязательно

| Требование | Почему важно | Как проверить |
|---|---|---|
| **PowerShell 7+** (`pwsh`) | Windows PowerShell 5.1 не умеет часть приёмов, используемых в рендере | `pwsh -v` |
| **Терминал с поддержкой Sixel** | Настоящие пиксельные кадры вместо символов | Windows Terminal, WezTerm, foot, Xterm с sixel-патчем |
| **chafa** | Конвертирует PNG/JPG в Sixel-поток для терминала | `chafa --version` |
| **Truecolor (24 бит)** | Белый/красный/зелёный без потери оттенков | — |
| **Моноширинный шрифт** | Сетка Sixel и панелей выравнивается по ячейкам | см. ниже |

### Высота окна — главный фактор качества

Проект сам подстраивается под окно, но **вертикаль решает всё**:

| Высота окна | Что видно |
|---|---|
| **≥ 44 строки** | Полная картина: отчёт Cyberdyne целиком **и** прокрутка ТТХ |
| 34–43 строки | Отчёт целиком, ТТХ частично (3–13 строк) |
| 30–33 строки | Отчёт целиком, ТТХ пропускается |
| < 30 строк | Отчёт обрезается, в лог пишется WARN |

Шапка юнита занимает 7 строк, итоговый отчёт — ещё 13. **Рекомендуется
максимизированное окно на 1920×1080 с размером шрифта 12–14 px — это даёт
40–50 строк.**

### Шрифт

Windows Terminal выравнивает экран по ячейкам, поэтому **пропорциональный шрифт
ломает всю вёрстку**: разъезжаются панели, стрелки аннотаций и подписи.

Проект сам подбирает шрифт и **проверяет его на моноширинность** измерением ширины
глифов. Приоритет: `Unispace` → `Eurostile` / `Microgramma` / `Michroma` →
`Rajdhani` / `Orbitron` / `Share Tech Mono` → `Consolas`.

> **Unispace** — квадратный техно-шрифт с равномерной сеткой, ближе всего к экранам
> Cyberdyne из «Терминатора» (1987). Шрифт с экранов фильма сделан вручную для
> студии, готовой копии в Windows нет.

Профиль `SkyNet HiRes` создаётся автоматически в
`%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\SkyNet\skynet.json`
при каждом запуске.

### Производительность

Сцена T-800 показывает все 215 кадров. Реальная частота ограничена скоростью
работы самого chafa, а не задержками в коде. На SSD и быстром CPU один полный
проход занимает 12–20 секунд.

## Как это работает

### Слои

```
Core/launch_skynet.ps1          ← точка входа шоу
   ├── config/skynet.json       ← все настройки (версия, размеры, анимация)
   ├── SkyNet.Core              ← конфиг, геометрия окна, логирование
   ├── SkyNet.Log               ← ротация логов
   ├── SkyNet.Anim              ← бегущая строка, fade, анимации
   ├── SkyNet.Glitch            ← глитч-эффекты строк
   ├── SkyNet.UI                ← общие примитивы вывода
   ├── SkyNet.Render            ← поиск chafa, Sixel-вывод, truecolor
   ├── SkyNet.Boot              ← boot-последовательность
   ├── SkyNet.T800              ← кадры, ТТХ, спец-рендер T-800
   ├── SkyNet.Prologue          ← вступительная сцена
   └── SkyNet.Finale            ← финальная сцена и звонок
```

Модули независимы и общаются через `$GLOBAL:_SkyNetCore` и цветовые
переменные (`ColPrologue`, `ColAccent`, …). Каждый экспортирует только свои
функции через `Export-ModuleMember`.

### Порядок сцен

У каждой сцены в третьей колонке указаны **курки звука** из таблицы
[«Карта звука»](#карта-звука-что-за-что-отвечает) — чтобы ориентироваться, что
и где звучит, можно прямо по ходу шоу. Курок = смысл (`glitch`, `lost`, `boot`),
файл подставляется из цепочки, см. раздел про замену звуков.

**0. Пролог** (`SkyNet.Prologue`) — белый монохромный стиль:

| # | Сцена | Что выводится на экран | Курки звука |
|---|---|---|---|
| 1 | `Show-SkynetSshIntro` | `[ SSH SESSION ESTABLISHED ]`, `[ REMOTE TERMINAL DETECTED ]`, `HOST SCAN` с реальными данными компьютера, мигающий `SYSTEM ONLINE` | `step`, `online` |
| 2 | `Show-SkynetTerminalHijack` | пустые строки `PS C:\Users\…>`, затем `CONNECTION OVERRIDE` и перехват терминала | `prompt`, `hijack`, `override` |
| 3 | `Show-SkynetLogoNoiseReveal` | логотип собирается из шума **построчно**, с разрывами строк | `glitch` |
| 4 | `Show-SkynetSixelLogo` | финальный Sixel-кадр логотипа (настоящие пиксели) | — |
| 5 | `Show-SkynetOnlineBlink` | мигающее `SKYNET SYSTEM ONLINE` под логотипом | `online` |
| 6 | `Show-SkynetRadarBoot` | `GLOBAL DEFENSE NETWORK`, `INITIALIZATION`, время, `TARGET ACQUISITION SYSTEM` / `ONLINE`, затем строки `> SEARCHING FOR UNIT…` | `radar`, `radar_line` |
| 7 | `Show-SkynetUnitScan` → `Show-SkynetBodyScan` | **все 215 кадров T-800**: справа Sixel-видеоряд, слева панель зон, под ней отчёт Cyberdyne и прокрутка ТТХ | `zone`, `zone_done`, `scan` |
| 8 | `Show-SkynetOpticalCheck` | чек-лист `OPTICAL SYSTEM` | `ok` |

#### Голова и торс — это один ряд кадров

Отдельной «сцены торса» в шоу нет. `Show-SkynetUnitScan` внутри вызывает
`Show-SkynetBodyScan`, а тот крутит **всю папку целиком**: 215 кадров = голова,
торс и полный обход юнита в одном непрерывном проходе.

`Show-SkynetTorsoScan` остался в коде как запасной путь для *другого* набора
кадров и вызывается только при наличии папки `assets\torso_frames`. Такой папки
нет, поэтому сцена всегда пропускается с записью в лог
(`Prologue: сцена торса пропущена — отдельной папки кадров нет`). Если
положить туда кадры — добавится второй проход вращения.

**1. Основное шоу** (`Core/launch_skynet.ps1`):

| Сцена | Что выводится на экран | Курки звука |
|---|---|---|
| `Start-SkynetBootSequence` | `[INIT] Cyberdyne Systems…`, три `[OK] …`, поток `[MEM] 0x…` на весь экран, пять итоговых статусов | `boot`, `type1`…`type4`, `mem`, `status`, `online`, `alert`, `ok` |
| `Show-SkynetTerminatorFinale` | чёрный экран → **отдельное окно видеозвонка** с 137 кадрами T-800 → обрыв связи (Malwarebytes) → `I'll be back` → терминал уменьшается до рабочего размера | `connect`, `glitch`, `glitch_hard`, `lost`, `blocked`, `final` |

**2. Финал:** статус `AWAITING ORDERS, HUMAN.` — курок `ok`.

Фон всего прогона — `ambient_radar`, зацикливается на общей громкости.

> **Когда показывается оранжевая панель T-800.** Сцена `Show-SkynetT800Scene`
> (оранжевая панель ТТХ) запускается только если пролог **не** выполнялся —
> при `-SkipLogo`, `-Instant` или если логотип не найден. При обычном запуске
> пролог уже показал все 215 кадров, поэтому повторного прохода нет
> (`launch_skynet.ps1`: `if (-not $NoT800 -and -not $script:PrologueRan)`).


### Сцена сканирования T-800

Самая технически интересная часть. Двухслойная композиция: **справа** —
вращающиеся кадры как настоящий Sixel, **слева** — панель в отдельных колонках.
Слои не затирают друг друга: каждый рисует по абсолютной позиции, без `ESC[K`
до конца строки.

Панель слева:

- **7 строк аннотаций** накапливаются по мере прохода кадров. Активная строка
  мигает, предыдущие остаются на месте. Зоны привязаны к диапазонам кадров:

  | Кадры | Зона |
  |---|---|
  | 97–106 | `NEURAL PROCESSOR SCAN` |
  | 107–116 | `LEARNING COMPUTER SCAN` |
  | 117–126 | `OPTICAL/ACOUSTIC SENSOR SCAN` |
  | 127–136 | `POWER CORE SCAN` |
  | 137–166 | `HYPER-ALLOY COMBAT CHASSIS SCAN` |
  | 167–196 | `HYDRAULIC SERVO SCAN` |
  | 197–215 | `FULL-BODY SCAN` |

- После последнего кадра панель зон заменяется **итоговым отчётом**:

```
PROCESSOR SCANNING DONE CYBERDYNE SYSTEMS MODEL 101
INITIATING SYSTEM DIAGNOSTICS...

NEURAL PROCESSOR SCAN --> COMPLETE
LEARNING COMPUTER SCAN --> COMPLETE
OPTICAL/ACOUSTIC SENSOR SCAN --> COMPLETE
POWER CORE SCAN --> COMPLETE
HYPER-ALLOY COMBAT CHASSIS SCAN --> COMPLETE
HYDRAULIC SERVO SCAN --> COMPLETE
FULL-BODY SCAN --> COMPLETE

STATUS: ALL SYSTEMS NOMINAL
MISSION READY.
```

- Ниже прокручиваются строки ТТХ из файла
  `tactical and technical specifications.MD`.

**Отчёт важнее прокрутки ТТХ.** Если окно невысокое, отчёт получает все
доступные строки, а ТТХ пропускается с записью в лог. Молчаливого обрезания нет.

### Точное таймирование

`Start-Sleep` в Windows округляет значения меньше 15 мс до тика планировщика,
поэтому 2 и 4 мс фактически совпадают. Функция `Wait-SkynetPrologueDelay`
отдаёт длинную часть ожидания планировщику, а последние 8 мс выдерживает через
`Stopwatch`/`SpinWait`. Это сохраняет реальную разницу между интервалами и не
сбивает темп Sixel-кадров.

## Звуковое сопровождение

Опционально. Модуль `SkyNet.Audio` + класс `SkyAudio.cs` (WinMM, `winmm.dll`).

### Почему звук вешается на события, а не на общую дорожку

Шоу управляется **состояниями**, а не временем: кадры Sixel выводятся с той
скоростью, с какой их успевает обработать chafa, глитчи бросаются через
`Get-Random`, зоны переключаются по номерам кадров. Аудиодорожка фиксированной
длины разъехалась бы на десятки секунд. Поэтому здесь только короткие фразы в
конкретных точках кода — рассинхрон невозможен по построению.

### Карта звука: что за что отвечает

Сцена не знает имён файлов — она запрашивает **курок** (`glitch`, `lost`,
`boot`), а слой звука берёт первый доступный файл из цепочки курка. Чтобы
заменить звук, достаточно положить файл с нужным именем в `assets/audio` —
код менять не нужно.

**Плотные сцены** (`step`, `mem`, `scan`, `prompt`) срабатывают каждые
40–250 мс → нужен файл **30–150 мс**.
**Акценты** (`boot`, `zone`, `hijack`, `lost`, `final`) → уместны **0.5–3 с**.

| Сцена | Курок | Играет сейчас | Цепочка (запасные варианты) |
|---|---|---|---|
| Пустые строки `PS C:\Users\…>` | `prompt` | `key_01` 40 мс | `key_01` → `key_02` |
| Терминал перехвачен | `hijack` | `1` 793 мс | `1` → `glitch2` → `zone_done` |
| `CONNECTION OVERRIDE` | `override` | `optical_ok1` 783 мс | `optical_ok1` → `optical_ok` |
| Строка SSH/boot-текста | `step` | `key_02` 45 мс | `key_02` → `key_01` → `key_03` → `key_04` |
| Мигание `SYSTEM ONLINE` | `online` | `online` 185 мс | `online` → `optical_ok` |
| Пинг радара | `radar` | `radar_sweep` 3,6 с | `radar_sweep` → `zone_scan` → `key_02` |
| Строка отчёта радара `> …` | `radar_line` | `optical_ok1` 0,78 с | `optical_ok1` → `optical_ok` → `key_02` |
| Символ прокрутки ТТХ | `scan` | `key_02` 45 мс | `key_02`/`key_03`/`key_01` (запасные) |
| Смена зоны сканирования | `zone` | `radar_sweep1` 28,2 с | `radar_sweep1` → `zone_scan` → `key_01` |
| Зона подтверждена | `zone_done` | `zone_done` 461 мс | `zone_done` → `optical_ok` |
| Галочка «OK» оптики | `ok` | `optical_ok` 185 мс | `optical_ok` → `online` |
| Строка `[INIT]/[OK]` | `boot` | `boot_step` 3.2 с | `boot_step` → `key_02` → `key_01` → `boot_step1` |
| Набор `[INIT] Cyberdyne…` | `type1` | `key_03` 71 мс | `key_03` → `key_02` → `key_01` → `key_04` |
| Набор `[OK] Loading…` | `type2` | `key_02` 91 мс | `key_02` → `key_01` → `key_04` → `key_03` |

| Строка `[MEM]` дампа памяти | `mem` | `key_03` 35 мс | `key_03` → `key_02` → `key_04` → `key_01` |
| Баннер загрузки | `status` | `optical_ok` 185 мс | `optical_ok` → `online` |
| Итог `STATUS: ONLINE` | `online` | `online` 185 мс | `online` → `optical_ok` |
| Итоги `DEFENSE LINKS` / `NEURAL NET` | `status` | `optical_ok` 185 мс | `optical_ok` → `online` |
| Итог `HUMAN AUTH: BYPASSED` | `alert` | `glitch2` 461 мс | `glitch2` → `1` → `glitch` |
| Итог `AWAITING ORDERS` | `ok` | `optical_ok` 185 мс | `optical_ok` → `online` |
| **Любой фриз/разрыв кадра** | `glitch` | `glitch` 557 мс | `glitch`/`glitch2`/`key_04` (запасные) |
| Жёсткий «провал сигнала» | `glitch_hard` | `glitch2` 461 мс | `glitch2` → `glitch` |
| Разрыв сборки логотипа | `glitch` | `glitch` 557 мс | `glitch` → `key_04` → `glitch2` |
| Открытие канала звонка | `connect` | `radar_sweep` 3,6 с | `radar_sweep` → `zone_scan` → `key_02` |
| `SIGNAL LOST :: UPLINK SEVERED` | `lost` | `glitch2` 461 мс | `glitch2` → `1` → `glitch` |
| `PROCESS BLOCKED` | `blocked` | `glitch2` 461 мс | `glitch2` → `glitch` → `zone_done` |
| **«I'll be back»** | `final` | `1` 783 мс | `1` → `optical_ok1` |
| Фон весь прогон | — | `ambient_radar` 161 с | зацикливается, на общей громкости |

### Курки вместо имён файлов

Таблица цепочек лежит в `Modules/SkyNet.Audio.psm1`, переменная
`$script:Cues` (в начале файла):

```
'glitch'     = @('glitch', 'key_04', 'glitch2')   # первый доступный, без перемешивания
'lost'       = @('glitch1', '1', 'glitch')        # приоритет: первый свободный
'boot'       = @('boot_step', 'key_02', 'key_01', 'boot_step1', 'zone_scan')
```

Это даёт три вещи, которых не было при жёстко прописанных именах:

* **Удаление или переименование файла глушит не сцену, а одну цепочку** —
  сцена продолжит звучать запасным вариантом.
* **Диагностика.** В конце прогона в лог пишется, для каких курков в пакете
  не нашлось ни одного файла: «`нет файла для курков: lost, final`».
  Раньше молчащая сцена не отличалась от сцены без вызова звука.
* **Проверка без шоу** — одна команда показывает текущее состояние:

```powershell
Import-Module .\Modules\SkyNet.Audio.psm1 -Force
Initialize-SkynetAudio | Out-Null
Get-SkynetSoundMap | Format-Table -AutoSize
```

### Посимвольный набор строк `[INIT]`/`[OK]`

Строки загрузки печатаются «печатной машинкой» и **щёлкают на каждый символ**,
причём у каждой строки своя «голос» клавиши: `key_03` → `key_02` → `key_04` →
`key_01` (`[INIT]`, `[OK] Loading`, `[OK] Establishing`, `[OK] Bypassing`).

Настройки в `config/skynet.json`, раздел `BootSequence`:

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `TypeSoundEnabled` | `true` | `false` — вернуть старое «акцент на строку» |
| `TypeDelayMs` | `12` | пауза между символами, мс |
| `TypeSoundThrottleMs` | `55` | минимальный интервал между щелчками, мс |
| `TypeLineAccent` | `false` | дополнительно играть длинный `boot_step` в конце строки |

Два момента, из-за которых это сделано именно так:

* **Четыре курка, а не одна цепочка.** `@('key_03','key_02','key_04','key_01')`
  одним курком **не даст** четырёх разных щелчков: по правилу цепочки первый
  файл играет всегда, а `key_0X` короче порога ре-trigger'а, поэтому всё
  справа молчало бы и все четыре строки звучали одинаково. Отдельный курок на
  строку — единственный способ получить четыре разных клавиши.
* **`TypeLineAccent` по умолчанию выключен.** `boot_step` длится 3,2 с, то есть
  перекрывает набор следующей строки; вместе с посимвольными щелчками это даёт
  кашу. Включается обратно одним ключом.

Набирается строка ~700 мс и звучит 11–12 щелчков с интервалом ~62 мс при длине
щелчка 71–101 мс — лёгкое перекрытие, как у настоящей клавиатуры. Раньше строка
печаталась за ~130 мс, и щелчок на каждый символ физически не помещался: 24
наложения по 71 мс.

### Выбор звука однозначный

Курок отдаёт **первый доступный** файл своей цепочки. Случайного выбора нет:
раньше часть курков перемешивалась, и одна и та же сцена звучала то своим
файлом, то чужим. Запасные варианты в цепочке срабатывают только когда
основного файла нет в пакете.

Троттлинг тоже свой у каждого курка. Общий счётчик был второй причиной
«то звук, то тишина»: фриз обновлял общую отметку времени, и щелчки
следующей строки отбрасывались как «слишком часто», хотя это был совсем
другой звук.

Проверяется автоматически:

```powershell
.\Tools\check_audio_determinism.ps1
```

Четыре проверки: 40 разрешений каждого курка дают одну и ту же цепочку, в
коде выбора звука нет `Get-Random`, два разных курка подряд дают два звука,
а два одинаковых — один (троттлинг работает).

### Как не дать карте разойтись с кодом

Таблица выше поддерживается вручную, поэтому у неё есть обычное свойство
устаревать. `Tools/check_audio_docs.ps1` сверяет её с живым кодом и говорит,
что именно разъехалось:

```powershell
.\Tools\check_audio_docs.ps1
```

Проверяет четыре вещи: все курки из `$script:Cues` упомянуты в README, в
README нет курков-призраков, колонка «Играет сейчас» совпадает с первым
файлом цепочки и нет мёртвых курков (объявленных, но нигде не вызываемых).
Код возврата 1 при расхождениях — можно повесить на CI или предкоммит.

### Почему длинный сэмпл не перезапускается

Пользовательский `boot_step` длится ~3.2 с, а сцена `[INIT]/[OK]` дёргает звук
каждые ~250 мс. Без защиты файл перезапускался бы 8 раз за 2 секунды —
получается не «шаг», а треск. Поэтому `Play-SkynetSound`:

* не перезапускает фразу длиннее 900 мс, пока она ещё играет;
* если основной вариант занят — берёт следующий по цепочке, а не молчит.

Именно поэтому в цепочке `boot` короткий щелчок стоит вторым: пока играет
длинный `boot_step`, сцена не молчит, а отчётливо щёлкает.

### Почему WinMM, а не SNDVOL

`SNDVOL`/`SoundPlayer` на каждый звук поднимают **процесс** — это 80…150 мс
лага. При выводе ТТХ по 2 мс на символ звук отставал бы на пол-экрана.
`waveOut` держит сэмпл в неуправляемой памяти и отдаёт его устройству сразу.
Замеренные накладные расходы одного вызова: **0.043 мс** при бюджете 2 мс на
символ, то есть около 2%.

Клавиатурный треск защищён троттлингом `Audio.KeyThrottleMs` (45 мс): иначе
поток символов звучал бы пулемётным тарахтением, а не ровным клацаньем.

### Звуковой пакет

Файлы `assets/audio/*.wav` — PCM 16 бит, моно, 44100 Гц. Всё, что не
`ambient_radar`, проигрывается как одноразовая фраза.

Стартовый набор **синтезируется** через ffmpeg (`Tools/generate_audio.ps1`),
а не берётся из фильма: это юридически чисто и технически верно — квадратные
волны, FM и фильтрованный шум дают нужный «холодный» sci-fi характер.

```powershell
.\Tools\generate_audio.ps1              # пересобрать весь пакет
.\Tools\generate_audio.ps1 -Preview     # и сразу прослушать
.\Tools\generate_audio.ps1 -Only online,glitch
```

Реальные записи (механическая клавиатура, сервоприводы T-800) кладутся в ту же
папку с теми же именами и перекрывают синтез — менять код не нужно.

### Как заменить звуки своими

Положите файлы в `assets/audio/` под теми же именами — и всё. Код менять не
надо, загрузчик берёт всё, что лежит в папке.

**Подойдут любые форматы:** mp3, ogg, flac, m4a, aac, opus, wma и wav —
в том числе с телефона (24 бита, 48 кГц, стерео). Неподходящее движку
конвертируется автоматически через ffmpeg при загрузке и кэшируется в
`cache\audio/`. Конвертировать вручную не нужно.

Ручная конвертация нужна только если хочется контролировать результат:

```powershell
ffmpeg -i мой_звук.mp3 -ar 44100 -ac 1 -c:a pcm_s16le assets\audio\online.wav
```

Если рядом лежат `online.wav` и `online.mp3`, побеждает **wav** — так
результат не зависит от порядка обхода папки.

| Имя файла | Курки, где используется | Особенности |
|---|---|---|
| `key_01`, `key_02`, `key_03`, `key_04` | `step`, `mem`, `scan`, `prompt`, запасные варианты | короткие, 35–50 мс; троттлинг 45 мс |
| `boot_step`, `boot_step1` | `boot` | узнаваемый акцент загрузки; **короткий щелчок в цепочке страхует от повторного запуска** |
| `zone_scan` | `zone`, `radar` | нарастающий свип, 3.2 с |
| `zone_done` | `zone_done` | короткое подтверждение |
| `online`, `optical_ok` | `online`, `ok`, `status` | бипы подтверждения |
| `optical_ok1` | `override`, `radar_line` | акцент «CONNECTION OVERRIDE» и строк отчёта радара |
| `glitch` | `glitch` | резкий сбой, 0,56 с |
| `glitch2` | `glitch_hard`, `alert`, `lost`, `blocked` | сбой и «провал сигнала», 0,46 с |
| `1` | `hijack`, `alert`, `lost`, `final` | акцент захвата/обрыва/финала, 0,79 с |
| `radar_sweep` | `radar`, `connect` | пинг радара, 3,6 с |
| `radar_sweep1` | `zone` | длинный свип, 28,2 с, **основной** для `zone` |
| `ambient_radar` | фоновый гул | **зацикливается**, на общей громкости |

Имя `ambient_radar` особенное: только этот файл крутится по кругу. Остальные —
одноразовые.

### Громкость: микшер и уровень самого файла

`Audio.Volume` — общая громкость, она тянет за собой **все** сэмплы сразу.
Отдельную фразу через неё поднять нельзя: громкость микшера WinMM живёт в
диапазоне 0..100, поэтому при значении 70 максимум — это `100/70 = 1.43`,
то есть **+3.1 дБ**. Этого хватает, чтобы сдвинуть фон или акцент, но не
фрагмент, который объективно тише остальных.

Поэтому в модуле два независимых механизма:

| Механизм | Где | Что делает |
|---|---|---|
| `AmbienceVolumeFactor`, `TrackVolumeFactors` | `SkyNet.Audio.psm1` | множитель **микшера** относительно общей громкости; применяется и при загрузке пакета, и при `Set-SkynetAudioVolume` |
| `TrackGainsDb` + `ApplyGain` в `SkyAudio.cs` | усиление **в PCM** при загрузке | поднимает конкретный файл на нужное число децибел; кэш в `cache\audio` не меняется, `Audio.Volume` по-прежнему управляет всем |

`radar_sweep1` — единственный файл с усилением: `+12 дБ`, потому что его RMS
равен −32.5 дБFS против −15…−18 дБFS у остальных. Выше колена −1.4 дБFS пики
мягко сжимаются (tanh), поэтому уровень растёт без клиппинга: −32.5 → −20.6 дБFS
RMS при пике ровно 0 дБFS. `ambient_radar` усиления не имеет намеренно: его пик
−1.0 дБFS, то есть файл уже у полной шкалы, и любой подъём даёт искажения.

Файлы `1.mp3` и `optical_ok1.mp3` больше не лежат без дела: они включены в
цепочки `hijack`, `lost`, `final` и `override`.

Если нужны дополнительные варианты клавиш — добавьте `key_05.wav`, они
подхватятся автоматически (движок берёт первые четыре).

**Генератор не затрёт ваши файлы:** `Tools/generate_audio.ps1` без ключей
оставляет на месте всё, что уже есть. Пересобрать пакет целиком поверх своих
записей можно только явно: `-Force`.

Битые или неподходящие файлы (не WAV, обрезанные, AAC) просто пропускаются с
записью в лог — шоу от этого не ломается.

## Запуск

### Почему шоу чинит $env:PATH

Windows Terminal — MSIX-пакет. Оболочка, запущенная из него, получает
окружение, собранное из графа пакетов: в `$env:PATH` остаются 2–4 папки
`WindowsApps`, и ни `cmd`, ни `git`, ни `python` не находятся:

```
PS C:\Users\<user>\Desktop\SkyNet> cmd /c systeminfo
cmd: Термин "cmd" не распознаётся как имя ...
```

Это не настройка профиля — воспроизводится на обычной вкладке с
`pwsh -NoProfile`. Поэтому первым делом шоу вызывает
`Restore-SkynetTerminalPath` (`Modules/SkyNet.Core.psm1`): PATH собирается
из реестра (Machine + User) и объединяется с текущим, без слепой замены и
без дублей. Функция идемпотентна, а в лог пишет, что именно сделала:

```
PATH восстановлен: 4 → 37 записей (добавлено 33).
Терминал запущен из MSIX-пакета (Windows Terminal) и получил урезанный PATH.
```

Это чинит не только терминал после шоу, но и поиск инструментов во время
него (`chafa`, `ffmpeg`, `wt.exe`).

### Основной способ

```powershell
.\Core\start_skynet_fullscreen.ps1
```

Создаёт профиль `SkyNet HiRes` в Windows Terminal, подбирает шрифт, открывает
максимизированное окно и запускает шоу с интерактивным промптом после завершения.

### Прямой запуск

```powershell
.\Core\launch_skynet.ps1
```

### Через Планировщик Windows

```cmd
arm_show.cmd
```

Создаёт задачу `SKYNET_SHOW` и запускает её — удобно для оформления в ярлык.

### Два подводных камня запуска

**Закрытый Windows Terminal.** Профиль `SkyNet HiRes` не хранится в `settings.json`:
лаунчер пишет его во фрагмент
`%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\SkyNet\skynet.json`, а
работающий Windows Terminal держит список профилей у себя и подхватывает
изменение файла с задержкой. Если терминал уже открыт, первый запуск может не
появиться — вкладка попросит профиль, которого экземпляр ещё не знает. Лечится
закрытием всех окон терминала и повторным запуском. Рабочий каталог вкладки
задан флагом `--startingDirectory`, поэтому запуск не зависит от кэша профиля и
не падает с `0x8007010B`, даже если профиль помнит уже удалённый каталог.

**Только интерактивная сессия.** Задача создаётся с `LogonType=Interactive`, то
есть шоу видно только тогда, когда пользователь залогинен в Windows. Из
фоновой сессии окно показаться не может — это не ошибка, а ограничение
Planned Tasks: у задачи нет рабочего стола. На другой машине шоу запускают
локально: распаковать архив релиза и выполнить `arm_show.cmd`.

### Полезные параметры

```powershell

.\Core\launch_skynet.ps1 -LogoColor Green   # зелёный фосфор вместо оригинала

```

## Как добавить свои кадры

Кадры T-800 читаются из папки в порядке возрастания **числа в имени** (`1`, `2`, …,
`10`, `100`), а не по алфавиту. Поддерживаются `png`, `jpg`, `jpeg`, `bmp`, `webp`.

Положите файлы в `assets/` (или укажите путь через `-T800FramesFolder`).

Если положить кадры в общую папку вместе с другими картинками, оставляйте имена
**чисто числовыми** — проект берёт только такие (`-NumericOnly`), чтобы случайно
не подхватить логотип.

Зоны сканирования привязаны к номерам кадров (`Get-SkynetScanStages`).
Последний кадр определяется автоматически: если добавить файлы `216+`,
появится зона `FULL-BODY SCAN`.

## Если процессор слабый: `assets_lite`

Сцена T-800 — единственная, где идёт непрерывный поток из 215 Sixel-кадров.
На слабом ноутбуке она идёт рывками. Причина **не в видеокарте** (chafa вообще
не использует GPU, а Windows Terminal рисует картинку ~640×646 пикселей), а в
том, что каждый кадр — это запуск нового процесса и большой объём текста.

В проекте лежит готовая облегчённая копия кадров: `assets_lite/` — те же
215 файлов, уменьшенных с 1248×1248 до 800×800.

| | `assets/` | `assets_lite/` |
|---|---|---|
| Размер кадра | 1248×1248 | 800×800 |
| Средний файл | 260 КБ | 124 КБ |
| Все 215 кадров | 54,6 МБ | 26,1 МБ |
| Время chafa на кадр | 35,5 мс | 30,4 мс |

**Выигрыш на chafa — 15%, на диске — в 2,1 раза.** Качество почти не меняется:
при шрифте Unispace 14 px область вывода 76×38 ячеек — это примерно 638×646
пикселей, то есть кадр 800×800 даже чуть больше, чем нужно.

### Как подключить — два способа

**1. Постоянная подмена (папка имеет приоритет над `assets/`):**

```bat
mkdir assets\t800_frames
copy assets_lite\*.jpg assets\t800_frames\
```

Вернуть originals — удалить папку:

```bat
rmdir /s /q assets\t800_frames
```

**2. Разовый запуск, файлы в проекте не меняются:**

```powershell
pwsh -File .\Core\launch_skynet.ps1 -T800FramesFolder .\assets_lite
```

Подробности и замеры — в `assets_lite/КАК_ПОДЛЮЧИТЬ.txt`.

### `assets_lite/terminator` — финальное видео

Второй набор в той же папке: 137 кадров появления T-800 для окна видеозвонка,
уменьшенных с 1920×1080 до 1280×720.

| | `assets/terminator/` | `assets_lite/terminator/` |
|---|---|---|
| Размер кадра | 1920×1080 | 1280×720 |
| Средний файл | 85 КБ | 47 КБ |
| Все 137 кадров | 11,4 МБ | **6,3 МБ** |
| Время chafa на кадр | 33,4 мс | **28,4 мс** |

Подключение:

```powershell
# разовый запуск

```

```bat

```

**Сброс кэша обязателен** — иначе останется кэш от старых кадров.

### Почему финал может тормозить даже при тёплом кэше

Финал не зовёт chafa на каждом кадре: `Core/play_call_window.ps1` заранее
рендерит все 137 кадров в `cache\finale_sixel/<ШИРИНА>x<ВЫСОТА>/`, а потом
только читает готовые файлы. **Папка кэша привязана к размеру окна звонка.**

На другом компьютере окно получается другого размера → кэш не находится →
все 137 кадров рендерятся заново при первом запуске. Это разовая операция на
4–5 секунд, после неё всё снова быстро. Если финал идёт рывками — просто
запустите шоу второй раз, кэш прогреется.

### Чего папка НЕ исправит

Честно о границах: на один кадр уходит около 60 мс, из них chafa — только
~30 мс. Остальное — вывод в терминал и обновление панелей, они от размера
файла не зависят. Половина времени внутри chafa — это запуск процесса
(~14 мс), он не зависит ни от чего.

Поэтому если шоу всё ещё тормозит, работают два других рычага:

- **область вывода.** Данные растут вместе с ней: 76×38 → 509 КБ на кадр,
  68×30 → 328 КБ, 60×26 → 248 КБ. Область считается автоматически из
  свободного места, поэтому **чем шире окно, тем тяжелее кадры** — на
  большом мониторе они сами собой становятся больше.
- **кэш Sixel-кадров** — убирает запуск chafa из цикла, но требует
  предварительного рендера. Сейчас применён только в финале.

**Версия PowerShell на скорость не влияет.** Замер на Windows PowerShell 5.1
и PowerShell 7.6 дал одинаковые 30 мс на кадр: Sixel рисует терминал,
PowerShell только передаёт байты. Устанавливать PowerShell 7 ради
производительности смысла нет.

## Как безопасно уйти из проекта

Работа в VS Code идёт в папке-репозитории. Если в этот момент переключить
папку на другой проект, несохранённый буфер редактора может пропасть. Перед
переключением запустите одну команду:

```powershell
.\Tools\safe_leave.ps1
```

Скрипт за один запуск делает три страховки:

1. **Запасной коммит.** Если есть незакоммиченные изменения, они
   фиксируются отдельным коммитом. Ничего не удаляется и не перезаписывается.
2. **Копия исходников на рабочий стол.** Папка
   `SkyNet_rescue_<дата>` содержит все 31 файлов кода (`.ps1`, `.psm1`,
   `.cs`, `.json`, `.md`, `.cmd`) и файл `RESCUE.txt` с состоянием
   репозитория. Она лежит **вне репозитория** и переживает переключение
   папки. Тяжёлое (`assets/`, кадры, `chafa.exe`) не копируется — оно
   большое и восстанавливается отдельно.
3. **Тег-якорь.** Ставится метка `anchor-<дата>`, к которой можно вернуться
   одной командой.

Если что-то пошло не так, вернуть состояние:

```powershell
git switch --detach anchor-20260927-193857
```

Либо просто скопировать файлы из папки `SkyNet_rescue_*` обратно.

### Если в редакторе конфликт сохранения

`Failed to save: The content of the file is newer` означает, что файл на диске
менялся, пока вкладка была открыта. В этом диалоге **нажимайте
`Revert File`** (значок ↺) — он подставит версию с диска. Кнопка
`Use your changes and overwrite` (значок ✓) зальёт устаревший буфер и
откатит последние правки.

## Решение проблем

| Симптом | Причина и решение |
|---|---|
| Вместо картинок символы | Терминал без Sixel. Поставьте Windows Terminal или WezTerm |
| `chafa не найден` | `winget install hpjansson.Chafa`, либо путь в `Render.ChafaPath` |
| Картинка «поехала», панели наезжают | Пропорциональный шрифт. Нужен моноширинный |
| Мало строк, отчёт обрезан | Увеличьте высоту окна или уменьши размер шрифта |
| Вёрстка разъезжается | Запустите в Windows Terminal, а не в conhost |
| Ничего не показано | Смотрите `logs\skynet_boot.log` — сцена пишет причину пропуска |

Логи: `logs\skynet_boot.log` (ротация, до 5 МБ).
